# Optional email/password accounts

User requested simple name/email/password registration and login, no email verification, no required login for existing pages. Implement directly within the authorized request; no extra approval gates.

Two localized pages /vi/login, /vi/register and English equivalents. Dark ocean form styling, show/hide password, errors, pending state. Registration signs in immediately. Home shows account name/logout when signed in, otherwise login/register links. Map, directory, shipping data stay public.

Next Server Actions + Neon, without a separate backend. Normalized unique email; display name 2–80 characters; password 15–128 Unicode characters for new accounts, no composition rules, never trimmed. Salted scrypt N=131072,r=8,p=1 hashes. Generic login failure and equivalent dummy-hash work for unknown users. 256-bit random session token in HttpOnly, SameSite=Lax cookie, Secure in production, expires seven days. Database stores only token digest; expiry and revocation checked on every session read. Registration account and initial session inserted atomically. POST Server Actions retain Next's origin checks. No arbitrary redirect destinations.

Tables: auth_users, auth_sessions, auth_rate_limits. Atomic persistent 15-minute limits: 10 login attempts per email, 5 registrations per email, global safety caps of 500 logins / 100 registrations per window. Per-email limits count successful and failed attempts. Already blocked emails do not consume the shared work budget. Client and server share Unicode validation without HTML UTF-16 length constraints. Rate-limit keys are hashed. User-visible retry guidance 15 minutes. Global cap is intentionally conservative for this initial low-traffic app. Session/rate-limit rows are retained for now; cleanup is a later operational task. Password reset, email verification, MFA, access gating and social sign-in are outside current scope.

Verify credential boundaries, salted hashing, timing-safe verification, opaque tokens, registration/login/duplicate behavior, rate limits and session revocation/expiry. Verify actual Neon tables and rollback-only transaction for database session/uniqueness behavior. Never create real test accounts on production.
